## 1. 结论先行

当前项目已经完成一个可编译、可启动、页面较为完整的 Windows Qt 串口驱动器调试工作台，
阶段成果可以概括为：

1. 建立了统一的桌面端产品骨架，共 21 个业务页面；
2. 建立了串口连接、握手、100 ms 心跳、参数读取、参数写入和遥测解析基础链路；
3. 覆盖了参考软件中的大部分配置页面，并把参数、故障码、回零轨迹和说明图整合到一个程序；
4. 实现了 200 项 Pn 参数的原始值文本导入/导出和较完整的实时示波器；
5. 形成了协议文档、参考程序分析和阶段汇总文档。

但当前版本仍是“可演示、可开始实机联调”的阶段版，不是生产交付版。主要原因不是界面数量不足，
而是设备闭环还不完整：

- 参数写入后没有设备确认、超时、重试和回读校验；
- 未实现故障码的实时解析，界面目前无法可靠判断“无故障”；
- 多条高风险命令缺少统一的设备状态联锁；
- 参数字典中仍存在同名参数对应不同含义的情况；
- 运动开始/停止尚未实现，回零页目前只有知识展示；
- 没有串口模拟器、帧回放和自动化测试；
- 全部关键设备动作仍缺少真实设备验证记录。

因此建议把当前成果定义为 **“0.2 阶段版 / 通信与配置工作台原型完成”**，下一阶段的首要目标
不是继续增加页面，而是把通信确认、安全联锁、参数字典和测试闭环做扎实。

### 2.2 项目阶段变化

项目经历了两条明显不同的产品路线：

旧版本围绕“EHA 十段力标定”构建，主流程为：

1. 连接 EHA 串口；
2. 通过 Modbus TCP 连接力传感器；
3. 初始化 EHA 参数、力值和质量基准；
4. 机器人把执行器下压到标定工具；

8. 生成检测曲线并导出 Excel 标定报告。

这条路线已经体现“串口驱动 + 外部传感器 + 自动化流程 + 报告输出”的完整业务思维，
但强绑定具体 EHA 产品和标定工装。

#### 当前路线：通用 KaiserStudio 调试工作台

2026-10-22 的重构把程序改造成通用伺服驱动器调试软件：

1. 保留 EHA 串口协议；

3. 按参考版 KaiserStudio 补齐参数、反馈、控制环、故障、回零、I/O 和备份页面；
4. 增加实时示波、参数模型和统一导航；
5. 2026-10-29 继续完善参数界面、示波器、备份恢复和应用配置。

这说明项目目标已经从“某款 EHA 的专用标定工具”转向“通用驱动器调试上位机”。
后续规划必须先确认是否需要继续兼容旧自动标定业务，否则容易在通用工作台之外重复建设。

## 3. 系统边界与“各端”定义

当前仓库只包含 PC 上位机，不包含驱动器固件、EtherCAT 主站或机器人程序源码。所谓“各端”应理解为：

| 端 | 所在位置 | 当前职责 |
|---|---|---|
| 用户界面端 | 各 `*page.cpp` | 展示、输入、确认、导航 |
| 应用编排端 | `MainWindow`、`ParameterModel` | 页面信号分发、业务确认、参数状态 |
| 通信协议端 | `DeviceSerialService` | 串口生命周期、帧构造、流式解析、发送队列 |
| 驱动器端 | 仓库外部的 EHA/伺服驱动器 | 执行命令、返回参数和遥测 |
| 文件与配置端 | `ParameterModel`、`PreferencesPage`、`MonitorPage` | TXT/CSV 文件、QSettings、波形记录 |
| 旧外部传感器端 | 旧分支历史代码 | Modbus TCP 力传感器、旧标定流程 |

驱动器端只能按现有协议文档和代码行为进行“黑盒假设”，不能从本仓库证明其固件行为。
正式联调时，设备端状态机、报警位、单位倍率和命令副作用都需要现场确认。

## 5. 总体业务流程

### 5.1 启动流程

1. `main()` 设置应用名称、组织名和版本；
2. 创建 `MainWindow`；
3. `MainWindow` 创建 21 个页面和共享参数模型；
4. 从 `QSettings` 读取启动画面、默认页面和语言选项；
5. 若启用启动画面，显示约 900 ms；
6. 默认进入“实时设备概览”或用户指定的默认页面。

注意：语言选项目前只是保存字符串，没有加载翻译文件，English 不会实际切换界面语言。

### 5.2 打开设备流程

1. 用户在通信页选择串口、波特率、数据位、校验和停止位；
2. `CommunicationPage` 发出 `openRequested`；
3. `DeviceSerialService::open()` 配置并打开 `QSerialPort`；
4. 打开成功后立即发送握手帧：
   `55 55 B9 9B 9B B9 AA AA`；
5. 50 ms 后启动 100 ms 心跳：
   `55 55 B6 B6 7B 7B AA AA`；
6. 每次心跳期间设备持续推送 `EF AD AB` 实时帧；
7. 页面收到 `connectionChanged(true)`，启用连接相关按钮并显示数据。

当前“已连接”只表示串口成功打开，并不表示已经收到握手响应、有效状态帧或稳定心跳。
如果设备未上电、协议不匹配或串口被占用，界面仍可能在短时间内显示“通信在线”。

### 5.3 实时数据流程

1. `QSerialPort::readyRead` 把新字节追加到接收缓冲区；
2. `parseBuffer()` 扫描 `EF AD` 帧头；
3. `EF AD AA` 被解析为 7 字节参数帧；
4. `EF AD AB` 被解析为 8 字节遥测帧；
5. 遥测帧更新统一 `Telemetry` 快照并发出 `telemetryUpdated`；
6. 顶部参数带和仪表盘按 50 ms 合并刷新；
7. 示波器单独接收每一帧，不按 UI 刷新周期抽样；
8. 断线时顶部数据被清空，但部分业务页面仍保留最后一次数值。

这套设计避免了高频串口帧直接阻塞 UI，也避免示波器使用低频定时器“漏点”。方向是正确的。

### 5.4 读取 200 项参数流程

1. 用户点击“读取参数”；
2. 若存在本地待写入修改，先询问是否覆盖；
3. `DeviceSerialService::readAllParameters()` 暂停心跳；
4. 清空发送队列和接收缓冲区；
5. 发送 `55 55 FE FE EF EF AA AA`；
6. 设备返回 `EF AD AA PnH PnL ValueH ValueL`；
7. 每个参数帧立即更新参数模型、驱动器信息页、反馈页、I/O 页和配置页；
8. 收到 `Pn199` 或累计 200 帧后认为读取完成；
9. 若 5 秒内未完成，则按超时结束；
10. 完成后恢复心跳。

当前完成条件只检查“收到 200 帧”或“收到 Pn199”，没有检查 0–199 是否唯一、是否有缺项、
是否重复以及是否乱序。因此设备异常、日志干扰或旧超时回调都可能导致错误的“读取完成”判断。

### 5.5 单参数修改流程

1. 参数页直接编辑值单元格；
2. `QTableWidget::itemChanged` 把输入交给 `ParameterModel::setData()`；
3. 模型转换为 16 位原始值；
4. `parameterEdited` 信号直接触发 `writeParameter()`；
5. 服务把 8 字节写帧放入串口队列，每 180 ms 发送一帧；
6. `writeParameter()` 在入队成功后立即返回；
7. `MainWindow` 随即调用 `markWritten()`，把参数标成“已同步”，并提示修改完成。

这是当前最重要的状态语义问题：入队成功和设备执行成功不是同一件事。若串口随后掉线、设备拒绝参数、
设备重启或队列被清空，界面仍会显示“已同步”。同时，文档描述为“回车后提交”，但代码路径是单元格
提交即写入，没有统一的单参数二次确认。

### 5.6 批量写入流程

1. 备份恢复页导入 TXT 或 CSV；
2. 文件中的参数进入“待写入”状态；
3. 用户点击“写入设备”；
4. `MainWindow::confirmWrite()` 显示前 8 项及总数；
5. 所有参数依次进入串口队列；
6. 每项入队成功后立即标记“已同步”。

同样没有设备确认、失败回滚、整体事务状态和逐项进度。读取参数时还会清空参数发送队列，
因此已标记成功但尚未真正发送的项可能被静默丢弃。

### 5.7 EEPROM 保存流程

1. 用户点击“保存参数”；
2. 显示写 EEPROM 的风险确认；
3. 向 `Pn152` 写 `1`；
4. 界面提示保存命令已发送。

当前没有等待设备确认，也没有重新读取参数验证保存结果。

### 5.8 使能、停止和故障复位流程

设备固定帧：

| 功能 | 帧 |
|---|---|
| 使能 | `55 55 12 12 21 21 AA AA` |
| 下使能/安全停止 | `55 55 ED ED DE DE AA AA` |
| 故障复位 | `55 55 DC DC CD CD AA AA` |

仪表盘、通信页和故障页都可以直接发送这些命令。当前没有统一的全局状态机来限制：

- 有故障时是否允许使能；
- 未收到有效状态帧时是否允许使能；
- 模式切换前是否已确认下使能；
- 命令是否已被设备接受；
- 命令发出后状态是否在预期时间内改变。

其中使能和故障复位属于高风险操作，通信页和仪表盘当前没有二次确认。

### 5.9 参数备份流程

1. 读取设备全部参数；
2. 参数模型保存 200 项原始值；
3. 导出为兼容参考版的 TXT：

```text
Pn000 9999
Pn001 2
...
Pn199 0
```

4. 导入 TXT 后逐行校验参数号和 0–65535 原始值；
5. 导入项进入“待写入”；
6. 用户再确认批量写入。

当前备份页只检查“至少有一项已确认”，不检查 200 项是否完整读取。因此部分读取后仍可能导出文件，
其中未读取参数会以内存默认值 `0` 或上一次设备残留值写出。参数文件也没有机型、固件、时间、
参数表版本和校验信息。

### 5.10 实时示波流程

1. 服务为每个 `EF AD AB` 遥测帧生成单调递增的 2 ms 逻辑时间戳；
2. 示波页把每个 `Telemetry` 快照放入无丢弃队列；
3. 5 ms 播放定时器按“2 ms/帧”的逻辑节奏从队列取帧；
4. 只把当前帧实际更新的通道追加到对应曲线；
5. 5 ms 渲染定时器把新增点转换为 `原始值 × K + B` 后刷新 OpenGL 曲线；
6. 10 ms Y 轴峰值网格、时间窗口、Auto/Manual Y 轴按当前可视范围计算；
7. 暂停或断开时先处理完队列中的最后一帧；
8. 波形保存为带版本头的 CSV，包含通道配置、原始采样和显示状态；
9. 读取波形时恢复原始采样、K/B、单位和可见性。

优点：

- 不由低频 UI 定时器抽样，避免丢失同一批串口帧中的中间值；
- 指令和反馈可成对显示；
- 数据和显示变换分离，保存的是原始采样；
- 支持通道组、比例、偏移、单位、缩放和平移。

局限：

- 所有历史采样永久保存在内存，没有环形缓冲或最大时长；
- 悬停查找采样和 Auto Y 轴会遍历大量历史点；
- 长时间高帧率运行后，内存、重绘和交互性能可能下降；
- 通道单位、方向和倍率仍有待实机确认。

### 5.11 特殊设备操作

| 操作 | 当前写入/发送 |
|---|---|
| 驱动器规格 | `Pn021` |
| 绝对位置清零 | `Pn101` 依次写 `0 → 1 → 0` |
| 磁极检测参数 | `Pn103`、`Pn110`、`Pn109`，并使能 `Pn050=1` |
| 磁极检测启动 | `55 55 7A A7 A7 7A AA AA` |
| 反馈输出类型 | `Pn124` |
| 反馈输出脉冲 | `Pn123/Pn122` |
| 数字输入配置 | `Pn013/Pn014` |
| 数字输出配置 | `Pn015/Pn016` |
| 参数复位 | `55 55 00 00 04 57 AA AA` |
| 参数保存 | `Pn152=1` |

这些路径大多有风险提示，但其安全联锁和实机效果尚未统一验证。

## 6. 各端任务执行流程

### 6.1 用户界面端

用户界面端的任务不是只负责“画控件”，而是完成：

1. 选择设备和串口参数；
2. 展示实时数据；
3. 对参数进行显示值/原始值转换；
4. 发起读取、写入、保存、复位、使能等命令；
5. 对部分高风险操作弹出确认；
6. 在离线、使能、故障、读取中等状态下调整按钮可用性；
7. 导入导出参数与波形文件；
8. 向用户报告成功、失败和进度。

当前实现的问题在于“命令已发出”经常被过早显示成“操作完成”，且不同页面的离线/使能/未知状态
处理规则不一致。

### 6.2 应用编排端

`MainWindow` 是当前业务中枢：

1. 创建全部页面；
2. 连接页面信号与串口服务；
3. 汇总遥测并分发；
4. 实现批量参数确认；
5. 实现 EEPROM 保存确认；
6. 实现参数复位确认；
7. 维护参数未写入计数；
8. 管理页面导航和关闭时的未保存修改提醒。

随着功能继续增加，建议把“命令执行”“设备状态”“安全联锁”从 `MainWindow` 中拆成独立模块，
否则所有页面都会继续依赖窗口类的内部状态。

### 6.3 串口通信端

`DeviceSerialService` 是唯一设备传输边界，任务包括：

1. 枚举串口；
2. 打开/关闭串口；
3. 握手；
4. 心跳；
5. 构造普通参数写帧；
6. 发送固定控制帧；
7. 管理写参数队列；
8. 拼接并扫描接收流；
9. 区分参数回包和遥测帧；
10. 输出原始收发日志；
11. 发布遥测和串口错误。

建议下一阶段把它继续拆成：

- `SerialTransport`：只负责字节收发；
- `EhaFrameCodec`：只负责帧编解码和校验；
- `CommandScheduler`：负责 180 ms 节流、超时、重试和确认；
- `DeviceSession`：连接状态、心跳健康和设备在线状态。

### 6.4 驱动器端

驱动器端在当前仓库中是不可见黑盒。上位机对它的假设包括：

- 115200 8N1；
- 握手后开始响应；
- 心跳缺失会停止遥测；
- 普通参数写帧无 CRC 和序号；
- 参数读取依赖 `Pn199` 或总数量；
- 状态帧 `0x05` 的 bit0 表示使能；
- 电流和电压按 0.01 倍率；
- Pn169 使用十进制符号位编码。

上述假设必须通过设备协议手册或实机波形逐项确认。不要根据“界面看起来正确”认定驱动器行为正确。

### 6.5 文件与配置端

当前有三类持久化：

| 类型 | 内容 | 位置/格式 |
|---|---|---|
| 参数备份 | `Pn000–Pn199` 原始值 | 用户选择 TXT |
| 波形记录 | 原始采样、通道 K/B、单位和显示状态 | 用户选择 CSV |
| 应用配置 | 启动画面、默认页面、语言字符串 | QSettings |

TXT 参数文件兼容性较好，但缺少元数据与完整性校验。波形 CSV 有版本头，格式设计优于参数文件。
故障历史和通信日志只在内存中，程序退出即丢失。

## 8. 串口协议与数据映射

### 8.1 发送帧

普通写参数：

```text
55 55 PnH PnL ValH ValL AA AA
```

固定控制帧：

| 用途 | 帧 |
|---|---|
| 握手 | `55 55 B9 9B 9B B9 AA AA` |
| 心跳，100 ms | `55 55 B6 B6 7B 7B AA AA` |
| 读取全部参数 | `55 55 FE FE EF EF AA AA` |
| 使能 | `55 55 12 12 21 21 AA AA` |
| 下使能 | `55 55 ED ED DE DE AA AA` |
| 故障复位 | `55 55 DC DC CD CD AA AA` |
| 磁极检测启动 | `55 55 7A A7 A7 7A AA AA` |
| 参数复位 | `55 55 00 00 04 57 AA AA` |

### 8.2 参数回包

```text
EF AD AA PnH PnL ValH ValL
```

固定 7 字节，大端序。

### 8.3 遥测帧

```text
EF AD AB Type B4 B5 B6 B7
```

固定 8 字节，载荷为大端 32 位数据。

| Type | 当前解释 | 代码中的处理 |
|---:|---|---|
| `0x01` | 位置指令 | 32 位无符号存入 `positionCommand` |
| `0x02` | 位置反馈 | 32 位有符号存入 `position` |
| `0x03` | 速度指令/速度 | 高 16 位有符号为指令，低 16 位有符号为示波速度 |
| `0x04` | 电流指令/电流 | 高低 16 位分别乘 0.01 |
| `0x05` | 状态字 | 保存 raw；仅 bit0 解释为使能 |
| `0x07` | 参数监视 | 32 位无符号 |
| `0x08` | 顶部电流 | 32 位有符号 × 0.01 |
| `0x09` | 顶部速度 | 32 位有符号 |
| `0x0A` | 多圈位置 | 32 位无符号 |
| `0x0B` | 单圈位置 | 32 位无符号 |
| `0x0C` | 位置反馈兼容帧 | 32 位有符号 |
| `0x12` | 位置误差 | 32 位有符号 |
| `0x1A` | 母线电压 | 32 位无符号 × 0.01 |

当前没有对以下关键语义的代码实现：

- 状态字中故障、告警、准备就绪等位；
- 故障码字段；
- 心跳超时和通信健康状态；
- 写参数成功/失败回执；
- 命令执行完成信号。

### 8.4 Pn169 编解码

规则：

- `0–9999` 表示非负逻辑值；
- `10000–19999` 表示对应负数。

示例：

| 逻辑值 | 写入值 |
|---:|---:|
| 100 | 100 |
| 0 | 0 |
| -100 | 10100 |
| -500 | 10500 |

当前 `ParameterCatalog::encodePn169()` 和 `decodePn169()` 已按该规则实现，并对范围做了截断。

### 9.2 参数状态

当前参数模型只有：

- 未读取；
- 已同步；

建议扩展为：

- 未读取；
- 已从设备读取；
- 本地已修改；
- 已进入发送队列；
- 已发送，等待回执；
- 设备已接受；
- 已回读确认；
- 写入失败；
- 超时；
- 被设备拒绝；
- 保存到 EEPROM 成功/失败。

### 9.3 安全状态

每个高风险操作至少要检查：

1. 设备是否在线；
2. 使能状态是否已知；
3. 是否处于允许操作的状态；
4. 是否存在故障；
5. 参数是否与机型匹配；
6. 用户是否完成二次确认；
7. 操作是否有超时和失败反馈。

当前多数页面只实现了第 1 项或第 6 项。

### 11.3 主要工程教训

1. **界面进度不等于业务闭环**。页面、字段和按钮很容易增加，设备端确认与异常处理更难但更关键；
2. **同一参数必须有唯一可信字典**。当前参数目录、配置页和参考分析存在冲突，会导致现场误操作；
3. **“发送成功”不能在业务层解释为“执行成功”**。需要明确传输、设备接收、设备执行、掉电保存四个层次；
4. **安全联锁必须集中**。分散在每个页面中容易出现某个入口遗漏检查；
5. **先建立可重复验证环境，再扩展页面**。没有模拟器和测试时，重构和修复风险较高；
6. **文档需要区分“参考软件能力”“本程序已实现”“实机已验证”**。当前部分描述容易让新成员高估完成度。

## 13. 当前问题与风险清单

### 13.1 P0：正式联调前必须处理

| 问题 | 证据 | 影响 |
|---|---|---|
| 参数入队即标记“已同步” | `mainwindow.cpp` 参数写入回调和 `markWritten()` | 掉线、拒绝或丢帧时状态错误 |
| 没有写参数回执/超时/重试 | `DeviceSerialService::writeParameter()` | 无法判断设备是否执行 |
| 故障码从未赋值 | `faultCode` 字段存在，但 `applyTelemetryByte()` 未写入 | 界面无法显示真实故障 |
| 高风险命令缺少统一联锁 | 使能、复位、磁检测、模式切换分散在各页 | 状态未知时仍可能下发危险命令 |
| 磁极检测未检查下使能 | `startPoleDetection()` 只检查连接和勾选 | 可能导致意外动作/过流 |
| 参数读取完成判定不验证唯一性和完整性 | 仅按 Pn199 或帧计数 | 可能错误宣称 200 项读取完成 |

### 13.2 P1：下一阶段应处理

| 问题 | 影响 |
|---|---|
| Pn 参数名称与控制环页面冲突 | 用户可能在错误含义下调参 |
| 部分读取后仍可导出全部 200 项 | 产生含 0 或旧设备值的错误备份 |
| 切换设备不清理旧参数和旧遥测 | 新设备页面显示旧值 |
| 读取时清空写队列 | 已标记成功的待写参数可能丢失 |
| 单次超时回调无请求代次编号 | 旧超时可能提前结束新一次读取 |
| 单元格提交直接写设备 | 与文档描述不一致，缺少确认 |
| 故障页按钮不随连接状态禁用 | 离线点击和错误路径较多 |
| 参数 TXT 无设备与版本元数据 | 跨机型恢复风险高 |
| 示波历史无上限 | 长时间运行内存和交互性能下降 |
| 通信日志固定 8 字节切分 | 7 字节参数回包日志错位 |
| 无串口模拟器/回放测试 | 协议改动无法稳定回归 |
| 编码器下拉框不从设备参数反推 | 页面默认选项可能与设备真实配置不一致 |

### 13.3 P2：产品质量与维护性问题

- 应用配置 English 仅保存，不加载翻译；
- 通信页默认状态文案固定为 115200 8N1，与用户可选配置可能不一致；
- CMake 写入支持 Qt6，但代码使用 `QTextStream::setCodec()` 等 Qt5 API，Qt6 兼容并未验证；
- 版本号在 `CMakeLists.txt`、`main.cpp`、侧栏和关于页中重复；
- `deploy/` 保存了多个包含 CMake 中间文件的构建目录，交付目录不够干净；
- 没有 CI、测试目录和测试目标；
- `AGP.h` 和旧界面文件与当前产品边界混在同一根目录，增加新成员理解成本。

## 17. 最终判断

这个项目已经完成了一次有价值的产品化重构：从单场景 EHA 标定工具演进为覆盖连接、参数、监控、
诊断和配置的通用驱动器工作台。当前代码结构比旧版更适合继续扩展，实时示波和参数模型也形成了
较好的基础。

真正决定下一阶段质量的，不是再增加多少页面，而是把以下三条主线做实：

1. **可信通信**：每条命令都有状态、超时、失败和确认；
2. **可信数据**：参数名称、单位、倍率、方向、状态位只有一个权威来源；
3. **可信安全**：所有高风险动作在设备状态未知或条件不满足时默认锁定。

完成这三条主线后，再实现运动和回零执行，项目才会从“功能看起来很全的调试原型”升级为
“可以进入现场联调和验收的工具”。
