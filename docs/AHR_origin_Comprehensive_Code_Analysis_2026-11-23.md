## 1. 结论摘要

当前 `AHR_origin` 不是 `KaiserStudio` 分支中的通用多页面驱动器调试工作台，而是一个专用
Windows Qt 标定程序，核心目标是：

1. 通过串口控制赛威德 EHA/ECM 驱动器；
2. 通过 Modbus TCP 读取外部力传感器；
3. 执行 11 点力检测；
4. 执行十段正反向力标定；
5. 执行力矩清零和质量补偿；
6. 通过 Microsoft Excel COM 输出标定报告。

当前源码可以在 Qt 5.15.2、MinGW 8.1 64-bit 环境下成功构建，构建产物为：

```text
build/Desktop_Qt_5_15_2_MinGW_64_bit-Release/EHAcontrol.exe
```

2026-11-23 已在本分支重新构建成功。

从业务成熟度看，当前是“专用标定原型/现场工具”，具备完整主流程，但距离可靠交付还有明显差距。
主要问题包括：

- 力传感器值未初始化，首次通信失败时可能使用未定义值；
- Modbus TCP 没有流式缓冲、请求关联和超时管理；
- 无有效检测数据时仍可能显示“测试通过”；
- 反向测试不参与通过/失败判断；
- “力矩清零”按钮在所有代码路径中都没有被启用；
- 参数读取只等待 Pn199，不验证目标参数是否完整；
- 初始化、检测、标定没有统一状态机，也无停止或取消；
- 嵌套事件循环允许用户重入流程，可能同时执行两套设备命令；
- 断开 EHA 串口不会断开力传感器，也不会停止 Modbus 轮询；
- 质量补偿没有执行 EEPROM 保存；
- Excel 是强制外部依赖，没有可测试的导出层；
- 没有自动化测试、模拟器或协议回放。

因此不建议在未处理 P0 问题前直接用于新的现场标定。

### 3.2 非构建文件说明

#### `AGP.h`

这是一份自定义 Modbus TCP 客户端，包含：

- 连接/关闭；
- 模式和力/速度/位置控制；
- 输入寄存器、保持寄存器、线圈读写；
- Modbus 异常码判断。

但它没有参与构建，当前程序实际在 `MainWindow::readModbusData()` 中手写 Modbus TCP 请求。

该文件目前还不能直接重新启用，因为：

- `AGP_connect()` 引用了不存在的 `HOST`；
- 没有完整的流式收包和 MBAP 长度校验；
- 请求和响应只靠同步 `recv()`，没有事务关联；
- 部分错误处理仍使用错误的函数码；
- 未检查部分读取长度。

#### `forcesensorworker.h`

这是对 `AGP` 的简单 QObject 包装，但：

- 未包含 `QObject` 定义；
- 未加入 CMake；
- 当前 `MainWindow` 没有使用它。

构造函数注释写着“启动力传感器连接线程”，但当前实现实际上没有创建 `QThread`，TCP 通信是
主线程中的异步 `QTcpSocket`。

#### `disui.*`

只有空构造函数，没有业务逻辑，也未构建。

#### `mainwindow_origin.ui` / `mainwindow_design.ui`

被 `.gitignore` 规则 `*_origin.*`、`*_design.*` 忽略，是本地设计过程文件，不参与产品行为。

## 4. 总体架构

### 4.1 架构图

```text
五步 QTabWidget UI
        │
        ▼
MainWindow
├─ QSerialPort：EHA 驱动器
├─ QTcpSocket：力传感器 Modbus TCP
├─ QTimer：100 ms EHA 心跳
├─ QTimer：1000 ms 力传感器轮询
├─ QEventLoop：步骤延时和参数读取等待
├─ Qt Charts：偏差曲线
└─ QAxObject：Microsoft Excel 报告
```

这是典型的“单窗口 + 单控制器”原型架构。所有职责都集中在一个类中：

- UI 编排；
- 设备连接；
- 协议收发；
- 自动流程；
- 数据缓存；
- 测试判断；
- 图表；
- Excel 导出；
- 错误日志。

### 4.2 架构优点

- 对专用工具来说，代码入口直观；
- 五步流程与现场操作顺序一致；
- 串口协议和 Modbus 请求都有直接实现；
- 关键步骤都会写入文本日志；
- 图表和报告能直接形成标定闭环；
- 使用 `QEventLoop` 延时，至少没有用 `QThread::sleep()` 冻结全部 UI。

### 4.3 架构限制

- `MainWindow` 承担全部职责，无法单独测试；
- UI 当前页被当作业务状态；
- 没有统一状态机；
- 没有命令队列、回执、超时和取消；
- 设备协议、传感器协议和报告格式强耦合；
- 自动化流程使用嵌套事件循环实现，天然存在重入；
- 原始成员变量没有统一初始化；
- 没有平台抽象，Windows Excel COM 直接进入业务代码。

## 5. UI 与步骤流程

### 5.1 页面结构

| 页面 | 主要控件 | 当前行为 |
|---|---|---|
| 步骤一 | 串口刷新、串口选择、IP、连接 | 同时连接 EHA 串口和力传感器 TCP |
| 步骤二 | EHA 检测、EHA 初始化 | 发送检测力序列或写入初始化参数 |
| 步骤三 | EHA 标定 | 写入 PN140–149、PN180–189 并保存 |
| 步骤四 | 力矩清零 | 有实现函数，但按钮永久禁用 |
| 步骤五 | 质量补偿、确认、EHA 检测 | 写 PN170；重复检测；生成报告 |

另有 5 个侧边步骤按钮和前后箭头：

- 箭头槽函数通过 `setupUi()` 自动连接到 `on_NextStep*_clicked()` 和
  `on_ForwardStep*_clicked()`；
- `STEP1`–`STEP5` 没有对应槽函数，本质上是状态指示；
- 用户也可以直接点击 `QTabWidget` 标签跳页。

### 5.2 步骤进度的真实判定

`ontabwidgetindexchanged()` 仅根据目标页索引把前面所有步骤标记为完成：

```cpp
for (int i = 0; i < index; ++i)
    markStepCompleted(i);
```

它不检查：

- 是否真的连接了设备；
- 是否收到握手响应；
- 是否完成初始化；
- 是否完成标定；
- 力传感器是否在线；
- 是否保存过参数。

因此“步骤五”在刚启动时直接点击标签也能显示为一、二、三、四步均完成。这是 UI 状态与实际
业务状态脱节的典型问题。

## 6. 端到端业务流程

### 6.1 启动

1. `main()` 创建 `QApplication`；
2. 将应用网络代理设置为无代理；
3. 创建 `MainWindow`；
4. 加载 `mainwindow.ui`；
5. 将中央区域固定为 1280×720；
6. 设置标题和图标；
7. 禁用初始化/标定/清零按钮；
8. 显示步骤一图片；
9. 建立 TCP、串口和定时器信号连接。

`m_readTimer` 和 `m_heartbeatTimer` 在构造时创建，但没有立即启动。

### 6.2 连接流程

用户点击“连接”后，当前代码依次执行：

1. 如果串口已打开，仅关闭串口、停止 EHA 心跳并返回；
2. 校验 IP 的正则格式；
3. 连接力传感器 IP 的 502 端口；
4. 启动 1000 ms Modbus 轮询；
5. 最多等待 1000 ms 的 TCP 连接；
6. 无论 TCP 是否连接成功，继续执行 EHA 连接；
7. 从串口组合框第一段文本提取 COM 口；
8. 打开 115200 8N1 串口；
9. 发送握手帧；
10. 等待 50 ms；
11. 写 `Pn002=79`；
12. 启动 100 ms EHA 心跳；
13. 自动切到步骤二。

这张流程图的实现有几个关键断点：

- 力传感器连接失败不会中止后续流程；
- 串口打开失败后，`EHAreset` 仍然在函数末尾被启用；
- `EHAcalibration` 在串口尝试打开之前就被启用；
- 断开 EHA 串口不会关闭 TCP、停止轮询或清理传感器状态；
- 没有处理 `QTcpSocket` 的连接错误、断开和超时信号；
- 没有处理 `QSerialPort::errorOccurred`。

### 6.3 EHA 握手与心跳

握手：

```text
55 55 B9 9B 9B B9 AA AA
```

心跳：

```text
55 55 B6 B6 7B 7B AA AA
```

当前握手没有等待或检查设备响应，只用 50 ms 固定延时。心跳发送也没有检查写入结果。

### 6.4 EHA 检测流程

检测力序列：

```text
0, 200, 400, 600, 800, 1000, 1200, 1400, 1600, 1800, 2000
```

正向：

1. 写 `Pn044` 为设定力；
2. 固定等待 2000 ms；
3. 读取当前 `sensorforceValue`；
4. 原始值除以 10；
5. 记录实际力和偏差。

反向：

1. 从 2000 开始倒序设置；
2. 每点同样等待 2000 ms；
3. 读取当前力传感器值。

结束后：

1. 写 `Pn044=0` 卸力；
2. 计算正向前 10 点的最大绝对偏差；
3. 打开偏差曲线；
4. 最大偏差小于 30 时显示“测试通过”。

业务问题：

- 力值为 0 是合法测量值，但代码用 `if (!sensorforceValue)` 当成读取失败；
- 反向值没有参与最大偏差和通过判断；
- 只绘制正向点；
- 没有要求力传感器已经连接；
- 没有校验样本时间是否晚于本次力命令；
- 没有“稳定窗口”，固定 2 秒后只取最后一次值；
- 没有检查 EHA 当前状态、故障、使能或机械姿态；
- 没有取消、停止或急停；
- 操作过程中按钮仍可点击，可能启动第二套检测或标定。

### 6.5 无数据仍可能显示测试通过

代码在开始时先把检测向量填成 0。若传感器未连接或每个采样都读取为 0：

- `m_testResults` 不会加入任何点；
- `maxDeviation` 保持 0；
- 图表为空；
- 结果判断仍然计算 `qAbs(0) < 30`；
- 最终显示“测试通过”。

这是当前最严重的业务正确性问题之一。

### 6.6 EHA 初始化流程

当前初始化命令顺序：

```text
Pn000 = 9999
Pn169 = 0
Pn172 = 3
Pn048 = 0
Pn170 = 0
Pn044 = 200
等待 2000 ms
Pn102 = 1
Pn102 = 0
Pn044 = 0
Pn152 = 0
Pn002 = 81
```

每一条 `sendData()` 内部又固定等待 200 ms。

代码注释意图为：

- Pn000：内部参数初始化/系统复位；
- Pn169：偏置清零；
- Pn172：内参初始化模式；
- Pn048：质量基准清零；
- Pn170：质量补偿清零；
- Pn044/Pn102：施加预紧力后触发力矩清零；
- Pn152=0：“切换到标定模式”；
- Pn002=81：显示位移。

风险：

- Pn000 如果确实触发系统复位，200 ms 后继续写后序参数是否可靠没有验证；
- `Pn152=0` 与协议文档中“Pn152=1 保存 EEPROM”的语义容易混淆；
- 未检查设备是否在线、是否正在运行；
- 未检查每条命令是否被设备接受；
- 初始化按钮没有前置确认和状态机锁。

### 6.7 EHA 标定流程

设定力：

```text
1000, 2000, 3000, 4000, 5000, 6000, 7000, 8000, 9000, 9999
```

正向：

1. 写 Pn044；
2. 等待 2000 ms；
3. 读取力传感器；
4. 传感器原始值 ÷ 10；
5. 写入 `Pn140–Pn149`。

反向：

1. 从 9999 倒序到 1000；
2. 写入 `Pn180–Pn189`。

结束：

1. Pn044=0 卸力；
2. Pn152=1 保存 EEPROM；
3. Pn002=79 切回力/转矩显示。

关键风险：

- 标定流程没有像检测流程那样检查 `sensorforceValue != 0`；
- 传感器离线时可能把 0 或旧值写入十段标定点；
- 随后直接执行 Pn152=1，把错误值保存进 EEPROM；
- 标定时没有二次确认、姿态确认、急停或取消；
- 没有检查“机器人已经下压到位”这一人工前提；
- 没有每点记录时间、稳定性、传感器质量和设备状态；
- 没有验证 20 个参数写入是否成功；
- 没有在保存后回读核对。

### 6.8 力矩清零流程

函数 `onEHAzeroButtonClicked()` 已经实现：

1. 写 Pn044=0；
2. 写 Pn044=200；
3. 等待 2000 ms；
4. 写 Pn102=1；
5. 写 Pn102=0；
6. 切回 Pn002=79；
7. 等待 2000 ms；
8. 写 Pn044=0。

但是搜索整个当前分支，`EHAzero` 只被设置为 `false`：

- 构造函数中 `false`；
- 连接时 `false`；
- 标定结束后再次 `false`；
- 没有任何位置设置为 `true`。

因此步骤四的核心按钮永远不会启用，正常用户无法从 UI 执行力矩清零。这是当前最直接的功能阻断。

### 6.9 质量补偿流程

`onEHAmassconfirmButtonClicked()`：

```text
Pn160 = 0
Pn170 = 用户输入
```

没有：

- 输入数字校验；
- 负值/范围校验；
- 小数点输入校验；
- 保存到 EEPROM；
- 回读 PN170；
- 执行确认；
- 设备在线检查。

输入框是普通 `QLineEdit`，未设置 validator。输入空字符串或非法文本时 `toInt()` 返回 0；
输入负数会转成 `quint16` 后形成大值。

### 6.10 参数读取流程

点击报告中的“输出标定报告”后，先调用 `readCalibParamsFromDevice()`：

1. 检查串口；
2. 预分配 10 个正向标定点、10 个反向标定点；
3. 停止 EHA 心跳；
4. 发送“读取全部参数”帧；
5. 进入嵌套 `QEventLoop`；
6. 等待 Pn199 或 5 秒超时；
7. 恢复心跳。

解析目标：

- Pn140–Pn149；
- Pn180–Pn189；
- Pn170。

风险：

- 预分配后向量长度始终满足导出检查，无法据此判断是否真的收到数据；
- 只等待 Pn199，不检查目标参数是否全部出现；
- 没有重复、缺项、乱序检查；
- 超时后可能仍有迟到帧；
- 读取期间没有禁用其他设备操作；
- 嵌套事件循环允许用户重新触发流程。

### 6.11 Excel 报告流程

报告模板：

```text
ECM1B2000标定报告.xlsx
```

构建时由 CMake 复制到可执行文件目录。

当前代码写入：

| 报告位置 | 内容 |
|---|---|
| `B2` | 设备编号 |
| `E6` | Pn170 |
| `C8:C18` | 正向检测实际力 |
| `D8:D18` | 反向检测实际力 |
| `H8:H17` | Pn140–Pn149 |
| `J8:J17` | Pn180–Pn189 |

模板还存在：

- 型号；
- Pn47；
- Pn52；
- Pn53；
- 版本；
- 自动计算公式；
- 正向/反向测试示例文字。

当前代码没有采集或填写 Pn47、Pn52、Pn53、版本等字段，因此报告可能保留模板内容或为空。

报告实现依赖：

- Windows；
- 本机安装 Microsoft Excel；
- ActiveX/COM；
- `QAxObject`。

这条路径不适合无界面服务器或自动化 CI。若 Excel 未安装、启动失败或单元格对象创建失败，
只能输出日志，且部分子对象访问没有空指针检查。

## 7. 串口协议实现分析

### 7.1 写参数帧

```text
55 55 PnH PnL ValH ValL AA AA
```

当前 `sendData()` 检查 `QSerialPort::write()` 返回值，但：

- 返回值成功只表示数据进入 Qt 缓冲区；
- 没有 `waitForBytesWritten()`；
- 没有设备回执；
- 没有重试；
- 没有参数白名单；
- 没有数值范围校验；
- 每次发送后固定进入 200 ms 嵌套事件循环。

### 7.2 实时遥测

```text
EF AD AB Type B4 B5 B6 B7
```

当前只真正使用：

- `0x07` 参数监视值，即界面实时力；

其余 `0x08`、`0x09`、`0x0A`、`0x0B`、`0x0C`、`0x1A` 仅有空 `case` 或注释，不显示也不保存。

这与“实时力监控”目标一致，但协议解析能力明显小于协议文档。

### 7.3 参数回包

```text
EF AD AA PnH PnL ValH ValL
```

只在读取标定参数阶段解析。普通运行时没有参数回包处理。

### 7.4 接收缓冲区问题

`onSerialReadyRead()` 每次追加新数据，然后从头扫描整个缓冲区：

- 已经处理过的遥测帧不会被删除；
- 新数据到来时会反复扫描旧帧；
- 随着运行时间增加，扫描成本逐渐提高；
- 缓冲区超过 4096 字节时直接截掉前段；
- 截断可能发生在帧中间；
- 参数读取和遥测共用同一缓冲区，但没有统一帧队列。

当前不会累计错误数据，因为重复遥测只是再次设置同一显示值，但这是低效且脆弱的设计。

## 8. 力传感器 Modbus TCP 分析

### 8.1 请求

每 1000 ms 发送：

- Modbus TCP；
- Unit ID 1；
- Function 0x03；
- 地址 1542；
- 数量 2 个寄存器。

代码从响应最后两个字节取第二个寄存器的值作为力值。

地址、两个寄存器的含义及寄存器顺序没有项目内文档，属于现场硬编码知识。

### 8.2 缺省初始化

`sensorforceValue` 在头文件中声明为：

```cpp
quint16 sensorforceValue;
```

没有初始化。

在第一次成功收到传感器响应前，检测流程若读取它，属于未定义行为。它可能为任意非零值，
从而被当作真实传感器数据。

### 8.3 响应解析

`onSocketReadyRead()` 直接 `readAll()` 后调用 `parseModbusResponse()`。

解析器假设一次 `readAll()` 正好得到一个至少 11 字节的完整响应：

- 不缓存半包；
- 不处理粘包；
- 不按 MBAP 的 Length 字段切帧；
- 不检查 transaction ID；
- 不检查 byte count；
- 不区分请求和响应；
- 不处理 Modbus Exception；
- 不检查两个寄存器中第一个的含义；
- 只检查 `length == 7`。

TCP 是字节流，这些假设在实际网络中不成立。

### 8.4 轮询与连接管理

没有：

- 请求超时；
- 重试；
- 在途请求限制；
- 响应关联；
- 传感器时间戳；
- 断线重连；
- `errorOccurred` 信号处理；
- 断开 EHA 时停止轮询；
- 关闭程序时明确关闭 TCP。

力传感器失败时，界面可能长期保留上一次的值，检测仍继续。

## 9. 数据与状态模型

### 9.1 当前实际状态

当前没有显式状态枚举，隐式状态来自：

- 串口是否打开；
- TCP 是否连接；
- 当前 Tab 索引；
- 布尔值 `m_waitingForCalibParams`；
- 若干按钮是否启用；
- 定时器是否运行。

这不足以表达业务状态。

### 9.2 建议状态

建议至少定义：

```text
Disconnected
EhaConnecting
SensorConnecting
Ready
DetectingForward
DetectingReverse
Initializing
CalibratingForward
CalibratingReverse
Saving
ReadingParameters
ReportGenerating
Failed
Cancelling
Completed
```

每种状态应规定：

- 可进入条件；
- 可执行命令；
- 可点击按钮；
- 超时；
- 取消方式；
- 失败后的安全动作；
- 允许生成的报告。

### 9.3 数据有效性

每个采样至少需要：

- 原始值；
- 单位换算值；
- 采集时间；
- 对应设定力；
- 力传感器连接状态；
- 是否为本次命令后的新样本；
- EHA 命令是否写入成功；
- 偏差；
- 数据质量标记。

当前只有值和有限调试日志。

## 14. 建议改造路线

### 阶段 A：先修复阻断和安全问题

1. 将 `sensorforceValue` 初始化为无效状态，并增加 `hasSensorSample`、`sampleTime`；
2. 用 `std::optional` 或独立有效性结构表示传感器采样；
3. 启用并规范 `EHAzero`；
4. 传感器失败或数据过期时禁止检测、标定和报告；
5. 空结果、缺测点不得判定为通过；
6. 反向测试纳入统计；
7. 增加全局“停止/取消”；
8. 增加流程运行锁，防止按钮重入；
9. 断开操作同时停止 TCP 和所有轮询；
10. 标定前增加明确确认，保存后回读关键参数。

### 阶段 B：重构通信层

建议拆成：

```text
EhaSerialClient
├─ open/handshake/heartbeat
├─ writeParameter()
├─ readParameters()
├─ frame decoder
└─ command timeout/result

ForceSensorClient
├─ ModbusTcpTransport
├─ MBAP stream decoder
├─ transaction correlation
├─ poll scheduler
└─ freshness/error state
```

要求：

- TCP 维护接收缓冲区；
- 按 MBAP Length 拆包；
- 校验 transaction ID、unit ID、function code、byte count；
- 每次轮询有超时；
- 新样本时间晚于本次力命令；
- 断线自动进入失败状态。

### 阶段 C：状态机化业务流程

将现有同步函数拆成异步状态机：

```text
Connect
  → SensorReady + EhaReady
  → DetectForward
  → DetectReverse
  → Init
  → CalibrateForward
  → CalibrateReverse
  → Save
  → Zero
  → MassCompensation
  → Verify
  → ExportReport
```

每个步骤：

- 开始前检查前置条件；
- 发出命令；
- 等待确认；
- 超时失败；
- 可取消；
- 输出结构化记录。

### 阶段 D：报告与数据

1. 建立独立 `CalibrationRun` 数据模型；
2. 记录设备编号、型号、软件版本、时间、工位、操作员；
3. 记录每个点的设定力、传感器值、时间、稳定性和偏差；
4. 报告导出优先使用可测试的 XLSX 库；
5. Excel COM 仅作为可选实现；
6. 保存原始 JSON/CSV 过程记录，便于追溯；
7. 报告生成后校验文件存在、大小和关键单元格。

### 阶段 E：测试与工程化

1. 为串口帧构造和解析编写单元测试；
2. 为 Modbus 分包、粘包、异常响应编写单元测试；
3. 制作串口和 Modbus 模拟器；
4. 使用无传感器空数据场景验证不能通过；
5. 增加连续运行和断线恢复测试；
6. 拆分 `MainWindow`；
7. 清理未构建代码和本地配置；
8. 建立 Release 安装包和版本信息。

## 17. 最终判断

`AHR_origin` 的核心业务已经搭建起来：五步 UI、双通信链路、力检测、十段标定、清零、补偿和
Excel 报告都已具备原型实现。它适合作为现场流程和协议知识的基线，但当前实现把大量时序、
业务有效性和安全条件交给固定延时、人工操作和未验证的返回值。

下一阶段应优先完成四件事：

1. 让所有数据有效；
2. 让所有命令有结果；
3. 让所有流程可取消；
4. 让测试能证明“失败不会被显示成成功”。

在这四点完成前，继续增加功能会放大现场风险，而不是提高项目成熟度。
